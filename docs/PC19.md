# PC-19 — MS `Proposal` · `tools.py` → ActionIntent (CMD-A2, 보고만)

이 문서는 조사 기록이다. MS 파일은 고치지 않았다. 실험은 MS 복사본에서 [`eval/pc19_probe.py`](../eval/pc19_probe.py)로 했다.
읽은 판본: MS `8b9f292` · Telemetry `70b4feb` · DC 통합 머리 (모두 `claude/gracious-meitner-vp49xe`).
기준: MS 시험 173 개, Telemetry · DC 를 옆에 두면 건너뜀 2 개.

## 1. 지금 MS 의 길

```
pipeline.run (판마다)
  CR.decide → provider → proposal_from(resp) → Proposal ─► Arbiter.decide ─► NOOP / DENY(다음 판) / ALLOW
                                                                              ├ retrieve: CR 안에서 행을 꺼냄(도구 실행 없음)
                                                                              └ 도구: tool.run(target, args) → [관측 dict] → StateManager.ingest
                                                                                     L0: tool.start / tool.end   ← action.* 이 아니다
runtime.handle (실행이 끝난 뒤)
  _record → DecisionRecord(id = 내용 해시) · RunRecord(decision_ref) → L0 run.end(decision_ref)
```

한 요청(DecisionRecord 하나)에서 도구는 **많아야 한 번** 실행된다. `pipeline.run` 이 실행 직후 끝나기 때문이다.

## 2. 칸별 대응

### Proposal (`ms/llm.py`) → ActionIntent

| Proposal | ActionIntent | 바뀌는 것 |
|---|---|---|
| `tool` | `action` | 이름만 바뀐다. **의도가 되지 않는 셋**: `error` 가 있음(A0) · `"none"`(NOOP) · `"retrieve"`(CR 안의 맥락 조작이고 실행기가 없다) |
| `target` | `target` | 같다. 실제 도구는 언제나 문자열이다(`parse_proposal` 이 막는다) |
| `args` | `args` | 같다. json_schema 모드의 문자열 args 는 이미 객체로 풀린다. 원문이 JSON 이므로 계약의 JSON 검사에 걸리지 않는다 |
| `rationale` | `rationale` | 같다. 500 자 자름은 MS 의 규칙이고 계약에는 제한이 없다(P4: 자름을 빼도 MS 시험 초록) |
| `error` | — | A0 이면 의도를 만들지 않는다. 까닭은 Arbiter 원장에 남는다 |
| `raw` | — | LLM 원문. 계약 밖이다(MS 에 남는다) |
| `key()` | — | A8 되풀이 열쇠. **`intent_id` 로 바꾸지 않는다**: intent_id 에는 rationale · dc_id · used_keys 가 들어가서, 같은 명령을 까닭만 바꿔 되풀이하면 놓친다 |
| — | `dc_id` | **새 칸.** DC 배선이면 `state_source["id"]`(DC `wiring.py` 의 `record.id`). **기본 길(`usage_model.snapshot`)에는 DC id 가 없다** → Q1 |
| — | `policy` | **새 칸.** MS 에는 판본이 넷 있다: `cr`(cr-3) · `context_policy.version` · `prompt_policy.version` · provider 선택 → Q2 |
| — | `used_keys` | **새 칸.** LLM 이면 STATE 로 보인 키다. 이것은 상한이고, LLM 이 실제로 쓴 키는 모른다. 규칙(BD-76 `default_action`)이면 그 규칙이 본 키 |
| — | `author_kind` | `llm`(Proposal) · `rule`(DC `default_action`) |

### `tools.py` 의 ToolSpec → ActionIntent 가 아니다

ToolSpec 은 ActionSpec(Model)의 투영이다(BD-31). 행동 꼴이 아니라 **판정과 실행의 재료**다.

| ToolSpec | 가는 곳 |
|---|---|
| `name` | ActionSpec 이름. ActionIntent.`action` 의 어휘 |
| `params` · `check_args` | VALIDATE A4 (Guard) |
| `preconditions` | GUARD A6 |
| `risk` · grants | GUARD A7 |
| `handler` · `run` · `effect` | **실행기(이 저장소, 나중에).** 돌려주는 관측 목록은 ActionOutcome 에 자리가 없다 → G2 |
| `card()` | CR (MS 에 남는다) |
| `RETRIEVE` | CR 안의 일. 의도가 아니다 |

### 실행 자리(`pipeline.py`) → ActionCommand · ActionOutcome

| 계약 칸 | MS 에서 나오는 값 |
|---|---|
| `ActionCommand.intent_id` | 위에서 만든 의도 |
| `ActionCommand.decision_ref` | `DecisionRecord.id`. **지금은 실행 뒤에 지어진다** → G1 |
| `action` · `target` · `args` | ALLOW 된 제안 그대로. MS 에는 SAFE_ACTION 이 없다 |
| `issued_at` | ALLOW 시각. MS 시계는 **초**(`time.time`)이고 계약은 unix_ms 다. 곱해서 넣는다(G4) |
| `deadline` | None. MS 에는 도구 기한이 없다 |
| `ActionOutcome.is_error` | `any(signal == "tool_error")` 또는 예외가 있음 |
| `exception` | `type(e).__name__`. MS 도 메시지는 L0 에 싣지 않는다 |
| `output_chars` · `elapsed_ms` | Recorder 가 잰다 |
| `exit_code` · `status_code` | None. MS 도구는 보고하지 않는다 |

## 4. 틈

- **G1** `DecisionRecord` 를 실행 **전에** 지어야 `ActionCommand.decision_ref` 를 채울 수 있다. P0 이 이것이 가능하고 id 가 그대로임을 보였다. 고칠 곳은 MS 의 `runtime.py` · `pipeline.py` 다.
- **G2** 도구가 돌려주는 관측(MS Telemetry dict, StateManager 입력)은 ActionOutcome(L0 action.result 칸)에 자리가 없다. 관측은 MS 에 남기고, 실행기는 그것을 불투명한 목록으로 돌려주는 쪽을 제안한다. 실행기를 지을 때 정한다.
- **G3** 지금 MS 의 실행은 L0 에 `tool.start` · `tool.end` 로 남는다. `action.*` 으로 옮기면 Telemetry 시험 2 개가 깨지고 Sensor 가 보는 사건이 바뀐다. 둘 다 내는 길(중복 기록)과 바꾸는 길이 있다 → Q3.
- **G4** 시각의 단위: MS 는 초, 계약은 ms.
- **G5** P3 의 시험 구멍. MS 세션에 알릴 정보다.
